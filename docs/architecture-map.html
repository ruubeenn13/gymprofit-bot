Una API central, un cliente móvil y un bot.

GymProFit son tres sistemas independientes. La API REST (Spring Boot) es la fuente de verdad; la app Android es el cliente del usuario; el bot de Discord añade la capa social y de juego. Cada sistema tiene su base de datos y solo se comunica por REST.

relaciones entre sistemas

app→api
REST completo, JWT de usuario (USER/ADMIN/GUEST). Auth, perfil, ejercicios, rutinas, sesiones, progreso, nutrición, mediciones, objetivos, logros, notificaciones y admin.
bot→api
REST acotado, cuenta de servicio (mismo /auth/login). Hoy solo auth + ejercicios, para /ejercicios y el ejercicio del día. /rutinas pendiente (vinculación: rol BOT + /bot/**).
api→fcm→app
Push. La app registra su token (POST /notificaciones/token); la API envía por Firebase a los DeviceToken del usuario y limpia los muertos.
api→ext
Imports de catálogo. ~800 ejercicios (wger + free-exercise-db) y alimentos (Open Food Facts), idempotentes, por el admin.
bot→discord
Gateway (JDA). Slash commands, botones, modales y eventos del servidor.
Aislamiento: dos bases de datos separadas — gymprofit_db (API) y gymprofit_bot (Aiven, bot). Ni la app ni el bot acceden a la BD de la app: todo dato de la app pasa por la API.

Capas simples: UI → red (singleton Retrofit) → REST. Sin repositorio, ViewModel ni Room; estado en PreferencesManager (prefs normales + cifradas) y UtilREST (tokens en memoria). Callbacks enqueue.

En capas: controller → service (IXxx+Xxx) → repository (JPA+jOOQ) → entity. DTOs con MapStruct (nunca entidades), JWT stateless, ddl-auto=validate (Flyway gobierna el esquema).
